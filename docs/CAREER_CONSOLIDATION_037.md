# 취업 게시판 통합 037~040

범위는 후기·톡톡·라운지·연구소와 공통 첨부다. 뉴스·채용공고·수집기·통계 대시보드는 변경하지 않는다.

## 최종 저장 구조

- `posts`: 제목·본문·작성자·익명 여부·상태·작성/수정 시각 등 공통 정보.
- `career`: `post_id`(PK/FK), `category_code`, `subcategory_code`, `details`(JSONB), `poll_options`(JSONB).
- `post_attachments`: 게시판 이미지와 톡톡 첨부. `(attachment_scope, attachment_id)` 복합키로 기존 ID 충돌을 구분한다.
- `career_lab_poll_votes`: 기존 투표 기록과 회원별 중복 방지 PK 유지. 게시글 FK는 `career`를 참조한다.

기존 물리 테이블 `career_posts`, `career_reviews`, `career_talks`, `career_lounges`, `career_labs`,
`career_lab_poll_options`, `career_talk_attachments`, `post_images` 8개를 제거하고
`career`, `post_attachments` 2개를 추가한다. 최종 순감소는 6개다.
기존 이름 8개는 호환 뷰로 남는다. 전체 실측 기준 변화는 84 → 77 → 78개다.

`career_content_writer.py`는 공통 정보와 취업 상세를 `posts`와 `career`에 나누어 쓰며,
서비스의 동일 트랜잭션으로 처리한다. 익명 여부는 `posts.is_anonymous`만 사용한다.

## 적용 순서

1. 대상 DB의 적용 이력과 구조를 확인하고 최신 백업을 만든다. 백업/연결 비밀정보는 Git에 넣지 않는다.
2. 백업을 별도 로컬 PostgreSQL 18 DB에 복원하고 미적용 SQL을 순서대로 검증한다.
3. 실제 서비스 계정 권한으로 작성·수정·투표를 검증한다. 소유자 계정 테스트만으로 권한 검증을 대체하지 않는다.
4. Aiven에 037·038이 이미 적용되어 있다면 이를 재실행하지 않고 039 → 040을 적용한다.
5. 데이터/호환 뷰/권한 검증이 끝난 뒤 새 백엔드를 배포한다.
6. 네 게시판·첨부·투표·익명 표시·XP·알림을 실제 화면에서 확인한다.

현재 워크플로는 backend 변경이 develop에 반영되면 자동 배포를 실행한다.
따라서 DB 전환과 검증을 마치기 전에는 이 PR을 머지하지 않는다.
로컬 .env 계정과 배포 서버 계정은 다를 수 있으므로 배포 대상의 연결 계정도 확인한다.

| SQL | 역할 |
|---|---|
| 037 | 상세·선택지를 posts에 임시 통합, 공통 첨부와 호환 뷰 생성 |
| 038 | 호환 함수의 검색 경로 및 PUBLIC 실행 권한 제한 |
| 039 | career 생성, 데이터 복사, posts → career 임시 동기화 |
| 040 | 호환 인터페이스/제약/권한을 career로 전환하고 posts의 전환용 컬럼 제거 |

039 이후에도 기존 코드가 posts 기반 호환 인터페이스를 사용한다.
새 저장 코드는 040 적용 이후에만 배포한다.
040은 기존 career_posts의 SELECT/INSERT/UPDATE 권한을 career로 이어 주고,
투표 계정에는 행 잠금에 필요한 SELECT와 UPDATE(post_id)를 부여한다.
취업 글 ID 변경은 트리거가 차단한다. DELETE나 PUBLIC의 새 쓰기 권한을 일괄 부여하지 않는다.

각 SQL은 재실행용이 아니다. 039가 성공하고 040이 실패했다면 원인을 해결하고 040만 재시도한다.
잠금 시간 초과 또는 데이터 검증 실패 시 해당 트랜잭션은 롤백한다.
RDS는 준비 후 현재 스키마와 이력을 확인하고 미적용 단계만 같은 순서로 검증·적용한다.

## 데이터 보존 및 복구

익명 여부는 기존 career_posts 값을 기준으로 보존한다. 선택지·첨부 ID, 투표, 파일 경로와 생성 시각을 유지한다.
037/040은 기존 인터페이스의 데이터를 전환 전후 비교한다. 비대상 데이터도 별도로 비교한다.
호환 뷰와 트리거는 기존 조회·저장 경로를 지원하므로 모든 호출부 전환 전까지 유지한다.
옛 상세 테이블의 직접 DELETE/TRUNCATE 대신 posts를 통해 게시글을 삭제한다.

코드를 되돌릴 때 기존 코드의 호환 뷰 경로를 사용할 수 있다.
DB 복구는 검증된 백업을 별도 DB에 복원하고 전환한다. 백업 이후의 쓰기는 먼저 보존·재적용한다.

## 검증 항목

- 네 유형 작성·조회·수정 및 지연 제약조건 검사.
- 익명 표시와 비공개 회사명, 첨부 등록·삭제와 ID 보존.
- 정상 투표·중복 투표·잘못된 선택지·투표 후 선택지 변경 차단.
- 테이블 소유자가 아닌 작성 계정과 투표 전용 계정의 실제 SQL 실행.
- 취업 데이터/투표/첨부 및 비대상 데이터 보존.
- posts의 career_category, career_subcategory, career_details, poll_options 제거 확인.
