이미지 사전 검사와 최종 검사는 서로 다른 시점의 상태를 확인한다. 두 검사를 합치거나
최종 UPDATE의 행 잠금을 제거하면 저장 중 다른 요청의 변경을 놓치므로 유지했다.
좋아요 지급의 회원·게시글 잠금, 중복 이력·지급 한도·레벨 정책 조회도 유지했다.
정책을 장기 캐시하지 않아 DB 정책 변경을 새 활동에 반영한다.

## 측정 조건과 결과

일회용 PostgreSQL 16, 로컬 TCP. 기준 fixture는 게시판 10개, 글 50,000건,
댓글 200,000건, LIKE/SCRAP 합계 480,000건, 방문 300,000건이다.
기능 검증용 글이 추가된 HTTP 측정 당시 자유게시판은 5,007건이었다.
명시적 ID 시드 후 시퀀스를 MAX(ID)에 맞췄다. 원격 Aiven 지연으로 환산하지 않았다.

SQL/저장소 비교는 HEAD 코드를 별도 모듈로 읽어 현재 코드와 같은 fixture에서 실행했다.
저장소 지연 시험 외에는 실제 로컬 DB/파일을 사용했다. SQL 계획은 1회 예열 후 5회,
HTTP는 1회 예열 후 3회의 중앙값이다. 병렬 실험과 Docker 복구 중 실패한 측정은
성공 결과와 구분했고, 중단된 검증은 DB 복구 후 재실행했다.

| 경로 | 기존/제한 전 | 개선 후 |
|---|---:|---:|
| 실제 글 목록 API | 420.42ms / 7,685,991 bytes / 5,007건 | 20.57ms / 25,128 bytes / 31건 수신·30건 표시 |
| 실제 공지 API → 미리보기 | 368.96ms / 7,682,879 bytes / 5,000건 | 8.42ms / 1,845 bytes / 2건 |
| 댓글 SQL, 일반 인덱스 전후 | 336.30ms | 0.167ms |
| 희귀 검색어 SQL, trigram 전후 | 79.45ms | 0.851ms |
| HOT repository 조회 | 174.46ms / 100건 | 169.31ms / 3건 |
| 명예 repository 조회 | 79.35ms / 100건 | 64.88ms / 3건 |
| 파일 저장을 500ms 지연시킨 경쟁 행 잠금 | 504.36ms | 22.74ms |

댓글 계획은 전체 순차 스캔에서 `idx_comments_post_id`를 사용하는 인덱스 조회로
바뀌었다. 검색 계획에는 trigram bitmap 인덱스가 사용됐다. 매우 짧거나 흔한 검색어는
planner가 다른 계획을 선택할 수 있다. 인기글은 전체 순위 집계가 필요하므로 3건 제한이
집계 비용까지 같은 비율로 줄이지는 않는다.

일반 목록의 이미지 메타데이터는 여전히 일괄 조회 1회다. 목록 API는 인증 1회,
게시판 권한 1회, 페이지 1회, 이미지 1회(행이 있을 때)로 총 SQL 4회였다.
인기 미리보기는 범위 권한 목록 확인을 포함해 총 5회였다.

JSON 글 수정의 업무 SQL은 **5 → 4회**, 게시판 자체 조회는 **2 → 1회**였다.
일반 글 등록도 게시판을 한 번 조회한다. XP 풀 최초 사용에는 ORM 초기화 SQL이 있어
찬 상태와 예열 상태를 구분했다. 예열 후 글/댓글 작성의 새 psycopg 연결은 **0개**였다.
댓글은 게시판/알림에서 같은 psycopg2 풀을 2회, XP에서 psycopg3 풀을 1회 대여했다.
XP·알림을 콘텐츠 트랜잭션에 합치지 않았다.

실제 방문 API는 인증 SQL 1회와 방문 집계 SQL 1회로 총 2회였다.
이는 드라이버 execute 계측 기준이며 psycopg2가 내부 전송하는 BEGIN/COMMIT을
별도 SQL로 세지 않았다. psycopg3 transaction scope의 제어 호출은 연결 증거에 포함했다.

## 배포 전제와 팀 결정

1. 기존 PR의 042 → 043 → 044 → 045 선행 순서를 지킨다. 기존 045 미커밋 변경을
   그대로 보존했으며, 댓글/검색 인덱스는 새 046·047에만 추가했다.
2. 046은 인덱스 생성 동안 쓰기 잠금이 필요하다. 047은 pg_trgm 설치 권한과 GIN
   디스크·쓰기 비용을 검토해야 한다. 둘 다 로컬 재실행을 확인했으며 공유 DB에는 적용하지 않았다.
   대규모 운영 DB는 점검 시간 또는 관리자의 별도 CONCURRENTLY 적용 계획이 필요하다.
3. 046·047은 성능 개선용이며 기동의 필수 데이터 정책으로 추가하지 않았다.
4. 배포 시 저장소 루트의 `shared/boardPolicy.json`도 백엔드와 함께 동기화해야 한다.
   향후 이 파일만 변경할 때에도 프론트 재빌드와 백엔드 재시작이 필요하다.
   현재 workflow의 path 필터는 shared-only 변경을 감지하지 않는다. GitHub/배포 설정은
   이번 요청에서 변경하지 않았으므로 두 배포를 수동 실행하거나 별도 승인 작업으로 필터를 보완한다.
5. 게시판 표시 이름을 DB의 안정적인 코드로 바꾸는 데이터/API 구조 변경은 하지 않았다.
   이름 기반 식별을 제거하려면 코드 컬럼·고유 제약·운영 데이터 이관과 응답 계약을 먼저 합의해야 한다.
   현재의 영속 이름/역할/반응 유형/시간대와 기존 접근 정책은 유지했다.
6. 커밋·푸시·병합·공유 DB 반영·운영 배포는 별도 요청 대상이다.

일회용 컨테이너·검증 전용 서버·Chrome 프로필·테스트 이미지/임시 스크립트는 검증 후 정리한다.
