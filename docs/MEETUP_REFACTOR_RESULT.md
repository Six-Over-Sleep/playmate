# 모임 백엔드 중복 처리 정리 결과

작업 브랜치: `feature/33-meetup-backend-function-fix`

## 변경 내용

- 기존 모임 목록 조회에 카테고리 조건을 전달해 필요한 종류만 DB에서 조회한다.
- 기존 목록의 좋아요 집계 결과를 재사용한다. 새 모임 목록에서는 확정 참여자와 본인의 대기 신청에 필요한 필드만 조회하고, 다른 사람의 커리어와 취소 이력을 읽지 않는다.
- 신청 저장 시 변경된 신청만 갱신하고 일괄 flush한다. 기존 모임 참여 테이블과의 호환 처리는 유지한다.
- 정원이 찬 모임은 대기자 순회를 즉시 종료한다. 승격 중 확정 인원과 기술 구성을 매번 전체 재계산하지 않는다.
- 예약 작업은 처리 시점에 도달한 모임만 조회한다. 같은 일정의 준비 이벤트를 반복 생성하지 않는다.
- 연결된 외부 전송 기능이 없으면 outbox 조회를 생략한다.
- 응답 조립은 `recruit_program_presenter.py`의 순수 함수로 분리하고 DB 조회는 Repository에 유지한다.

## 검증

- 모임 테스트, 기존 모집 마감·모임 소셜·게시판 API 회귀 테스트: **131개 통과**.
- 전용 임시 PostgreSQL에서 동시 신청·중복 신청·마이그레이션·실제 Router 연결·목록 JSON 필드 조회·예약 대상 조건을 검증했다. 검증 후 임시 컨테이너를 제거했다.
- 정원 초과 대기 100명·500명에서도 확정 인원 조회가 2회 이내인지 검증했다.
- 취소 이력 0건·100건에서 신규 신청의 flush 호출 횟수가 동일하고 4회 이내인지 검증했다. 이는 SQL 실행 횟수나 실제 응답 시간을 의미하지 않는다.
- 운동 목록에 해당 데이터가 없으면 SELECT 1회만 실행하며 신규 모임·신청 테이블을 조회하지 않는지 검증했다.
- 미래 모임에 예약 처리가 실행되지 않고, 마감 준비가 일정 버전별 한 번만 처리되는지 검증했다.

## 유지한 범위

API 응답 필드와 정책, 기존 모임 호환 데이터를 유지했다. 공유 DB와 이미 적용한 SQL 파일은 변경하지 않았다. 실제 OAuth·프론트엔드 통합 검증은 이 회귀 테스트와 별도이며, 운영 환경의 응답 시간 개선 수치는 측정하지 않았다. 커밋·푸시는 하지 않았다.
